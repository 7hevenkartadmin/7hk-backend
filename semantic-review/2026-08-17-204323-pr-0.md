# Retry-safe WhatsApp OTP login hardening with deployment diagnostics

This change hardens WhatsApp login from startup validation through OTP proof creation, transactional session completion, provider diagnostics, webhook processing, and deployment readiness. Exact credential grammars feed a bounded Redis proof, while a Mongo completion record makes ambiguous retries reproduce one token pair. Request correlation is retained through provider and webhook outcomes. Delayed replay and the self-attested readiness gate remain shipping blockers.

Watch for: **confirmed** replayed cookies can outlive their JWTs; **confirmed** a completed proof can overwrite a newer browser session with an obsolete refresh token; **confirmed** callback readiness can be opened using a handcrafted evidence file; **confirmed** the claimed completion/failure property coverage is not executed and required Mongo tests currently skip.

**Verdict**: NEEDS_CHANGES

## High-level view

Startup parsing now treats environment booleans as exact strings, rejects unimplemented providers, and validates Meta fields whenever Meta is selected. Phone and OTP inputs share exact route and service grammars, and invalid webhook signatures are rejected before the OTP service is resolved.

A correct OTP moves atomically from a Redis challenge into a time-bounded verified proof. MongoDB completion stores immutable issuance claims behind a proof digest and uses a unique index plus transactions to converge retries on one deterministic token pair. Replay does not account for elapsed time or subsequent refresh/logout state, so returned cookies and credentials can misrepresent the current session.

Provider outcomes and signed webhook statuses are correlated by request ID through Redis mappings and an allow-listed diagnostic schema. The readiness command does not derive its five checks from the deployed callback, diagnostics, or Meta configuration; it trusts booleans and labels in a local JSON file.

The unit, property, Redis, worker, webhook, and lint checks pass locally. Mongo transaction tests skip without a fixture, while the top-level bug-condition property uses source-string presence for the most important completion and cookie behaviors.

## Replayed cookies drift past immutable JWT expiry

**Confirmed.** `completedTokenPayload` reconstructs tokens from the completion's original issuance metadata (`src/modules/auth/auth.service.js:38-53`), but `attachCookies` gives every response a fresh `maxAge` of `exp - iat` (`src/modules/auth/auth.routes.js:24-36`, `src/modules/auth/token.service.js:159-173`). On delayed proof retry, the deterministic JWT keeps its original absolute `exp` while the cookie starts the full lifetime again. A local reproduction with a 15-minute token replayed two minutes after issuance produced 780 seconds of JWT validity and 899 seconds of cookie validity, a 120-second divergence.

Derive cookie lifetime from the token's remaining validity at attachment time and reject nonpositive remaining lifetime. Cover delayed completion replay under a controlled clock and compare cookie `Expires` directly with JWT `exp`.

## Completed proofs can restore an obsolete refresh cookie

**Confirmed.** Once a `LoginCompletion` exists, `completeVerifiedLogin` returns its stored token pair without checking the user's current `tokenVersion`, status, or `refreshTokenHash` (`src/modules/auth/auth.service.js:58-68`, `src/modules/auth/auth.service.js:168-171`). Refresh rotates `refreshTokenHash`; logout clears it and increments `tokenVersion` (`src/modules/auth/auth.service.js:112-131`). Resubmitting the same OTP while its proof remains alive can therefore overwrite the browser's valid rotated refresh cookie with the original token, or return a token pair already revoked by logout.

The stale pair does not bypass downstream token-version/status checks, but the endpoint reports success and can break a working refresh session. Compare completion metadata and the reconstructed refresh hash with current user state, then reject or close an obsolete proof rather than issuing revoked credentials. Cover refresh-then-retry, logout-then-retry, blocking, and token-version changes.

## Callback readiness is a self-attested JSON truth table

**Confirmed.** `runCallbackReadinessCommand` reads an arbitrary local evidence file and computes readiness from `passed: true` plus expected literal labels (`scripts/verify-whatsapp-callback-readiness.js:92-116`, `scripts/verify-whatsapp-callback-readiness.js:190-222`). It does not contact the public endpoint or Meta, inspect subscription state, consume correlated diagnostics, compare state around an invalid signature, verify freshness, or authenticate provenance. The positive test constructs all five claims in memory and reaches `ready: true` without a deployed callback (`tests/whatsapp-callback-readiness.test.js:25-57`, `tests/whatsapp-callback-readiness.test.js:198-215`).

A handcrafted file containing `origin: "META"`, `stateChanged: false`, and five passing booleans opens the gate. Require evidence produced by the systems performing the checks, including subscription inspection, a current-deployment diagnostic request ID, invalid-signature pre/post state, and freshness/run binding that labels alone cannot satisfy.

## Completion and failure-boundary tests do not execute their advertised properties

**Confirmed.** The bug-condition property treats source occurrences of `otp:verified:`, `LoginCompletion`, and `tokenLifetimeMs` as proof that retryability, idempotency, and cookie alignment work (`tests/whatsapp-login-bug-condition.property.test.js:75-87`). It does not inject user lookup/create/update, token generation, refresh persistence, ambiguous commit, or Redis cleanup failures. The Mongo suite covers concurrent success and blocked denial, but both tests call `t.skip` without transaction-capable Mongo (`tests/login-completion.test.js:96-113`); the local full run reported 136 passes and 2 skips.

Make required CI fail when Redis or transaction-capable Mongo is unavailable. Execute every downstream failure boundary, ambiguous commit resolution, delayed deterministic replay, and session-state transition instead of inferring behavior from source identifiers.
