# Retry-safe OTP completion with signed callback readiness evidence

This follow-up closes the delayed-cookie, obsolete-session replay, and non-executing completion-coverage blockers from the prior review. Cookie attachment now uses remaining JWT validity, completion replay checks current account/session state, and executable transaction models cover the downstream failure and ambiguity boundaries. The callback gate adds HMAC integrity, ten-minute freshness, deployment/run binding, and replay protection, but **confirmed** it still accepts handcrafted claims signed by the same generic repository helper rather than authenticating that deployed systems produced those claims.

Watch for: **confirmed** callback readiness remains self-attestable by any process with the shared HMAC key, including a process using the exported signer to construct all five facts without observing Meta or the deployed callback.

**Verdict**: NEEDS_CHANGES

## High-level view

Delayed deterministic replay now aligns each cookie with the JWT's absolute expiration by calculating remaining validity at attachment time. Replay also compares account status, token version, and persisted refresh hash before returning the immutable token pair, then terminally closes stale or blocked proofs.

The completion harness now executes lookup, create, update, token, refresh persistence, insert, ambiguous acknowledgement, and 2–20-way concurrency scenarios. Ordinary local validation passes with three explicit Mongo fixture skips; required-fixture mode converts exactly those missing transaction-fixture cases into failures, while Redis and BullMQ integration coverage executes successfully.

**Confirmed:** readiness evidence is tamper-evident, fresh, deployment-bound, run-bound, and single-use, but these properties authenticate only the document. The positive path creates arbitrary check objects, signs them with the configured shared key, and opens the gate without any trusted collector or deployed-system attestation.

External readiness remains an operator boundary. The public HTTPS callback still must be configured in Meta, pass GET verification, subscribe `messages`, complete one allow-listed smoke test, and produce fresh trusted evidence for valid-signature correlation and invalid-signature non-mutation.

## Shared-key signing does not establish deployed evidence provenance

**Confirmed.** `signCallbackReadinessEvidence` signs caller-supplied booleans and labels without obtaining or verifying any observation from Meta, the webhook, diagnostics, or state storage (`scripts/verify-whatsapp-callback-readiness.js:195-222`). Parsing verifies the HMAC and run window, then readiness is the conjunction of the embedded claims (`scripts/verify-whatsapp-callback-readiness.js:234-275`, `scripts/verify-whatsapp-callback-readiness.js:276-294`). Freshness, binding, and replay markers prevent stale or altered documents, but a newly fabricated document remains valid.

The positive test demonstrates the gap: `completeEvidence` builds all five check objects in memory and passes them to the exported signer (`tests/whatsapp-callback-readiness.test.js:44-78`), after which parsing reports ready without a deployed observation (`tests/whatsapp-callback-readiness.test.js:150-154`). The command-level success test uses the same handcrafted helper and reaches `ready: true` (`tests/whatsapp-callback-readiness.test.js:300-323`). This is the prior self-attestation failure with stronger document integrity around it.

Bind each fact to an independently trusted producer that actually performs or observes the check. Viable designs include source-specific attestations whose signing credentials are unavailable to the gate/operator process, or a trusted deployment collector that derives facts from Meta configuration, correlated backend diagnostics, and before/after state records and emits a constrained signed artifact. The repository gate must reject a generic HMAC over arbitrary caller-provided claims.
