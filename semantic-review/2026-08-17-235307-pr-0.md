# Retry-safe OTP completion with independently signed callback evidence

This regression pass confirms that the four original shipping blockers are resolved. Delayed replays now preserve the JWT’s absolute expiration, obsolete completions are rejected against current account/session state, the completion model executes failure and concurrency boundaries, and callback readiness accepts only fresh Ed25519-signed evidence from a configured producer key. Repository validation is complete; production callback readiness remains closed until an independent collector emits fresh deployed evidence, and required fixture validation remains intentionally red while transaction-capable MongoDB is unavailable.

Watch for: **confirmed** external callback evidence has not been supplied and the local MongoDB transaction fixture is unavailable; these are deployment/infrastructure prerequisites, not repository defects.

**Verdict**: APPROVED

## High-level view

Cookie attachment now derives remaining lifetime from each token’s immutable `exp`, so delayed deterministic replay cannot extend browser cookie validity beyond the JWT. Completion replay reconstructs the original token pair only while account status, token version, and persisted refresh hash still identify the same live session; refresh rotation, logout, blocking, and version changes close the proof instead of restoring stale credentials.

The callback gate now treats readiness as an independently authenticated artifact rather than an operator truth table. It loads only an Ed25519 SPKI public key, verifies canonical signed evidence, binds it to producer/environment/deployment/callback/run identifiers and a ten-minute window, and atomically rejects replay; production gate/operator code contains no private-key input or generic signer.

The focused and full suites execute property seeds `20260607` and `20260608`, Redis, BullMQ, Express, webhook, cookie, documentation, readiness, and executable completion-state coverage. Ordinary runs skip exactly three unavailable Mongo transaction cases, while required-fixture mode converts those same cases into expected failures and skips none.

## Absolute cookie expiry and live-session replay checks

**Confirmed.** `tokenLifetimeMs` computes cookie lifetime from `exp * 1000 - currentTimeMs`, rejects expired or malformed claims, and `attachCookies` calculates both lifetimes before attaching either cookie. Controlled-clock coverage verifies that a replay two minutes after issuance produces cookies ending at the original JWT expiration rather than restarting the full lifetime.

Completion replay derives the deterministic token pair from immutable completion metadata, then requires an active user, the completion’s token version, and a timing-safe match between the reconstructed refresh-token hash and the currently persisted refresh hash. Refresh rotation, logout, account blocking, and token-version changes raise `OTP_COMPLETION_STALE`; the OTP orchestration terminally denies that verified proof and fails closed if Redis cannot confirm closure.

## Ed25519 evidence establishes a separate collector boundary

**Confirmed.** The gate accepts a base64 DER Ed25519 public key and calls `crypto.verify` over canonical unsigned evidence. Signing-material inspection found `crypto.sign` and generated private keys only in `tests/whatsapp-callback-readiness.test.js`, where ephemeral keys construct synthetic fixtures; the production script has no signing export, private-key configuration, or code path that can manufacture passing evidence.

The signature covers the producer, environment, deployment, exact callback URL, UUID run ID, allow-list confirmation, five constrained facts, and their timestamps. Unsigned, tampered, stale, future-dated, overlong, incorrectly bound, wrong-key, and replayed evidence is rejected. Provenance depends on deployment controls provisioning the trusted collector’s public key without giving its private key to the gate/operator process; no external evidence was supplied, so production readiness remains false.

## Executable completion and fixture policy validation

**Confirmed.** The completion model executes user lookup, creation, update, token generation, refresh persistence, completion insertion, ambiguous commit acknowledgement, and 2–20 concurrent retry schedules. It also executes stale-session transitions and blocked-account denial; the three Mongo cases add real transaction integration when that fixture exists rather than substituting source-string assertions.

The focused command reported 99 tests, 96 passes, no failures, and three Mongo skips. `npm test` reported 168 tests, 165 passes, no failures, and the same skips. `npm run test:required-fixtures` reported 168 tests, 165 passes, three expected `ECONNREFUSED 127.0.0.1:27017` failures, and zero skips, demonstrating that required CI/pre-production validation fails closed.

Redis proof/correlation tests and the BullMQ worker fixture executed. `npm run lint`, `git diff --check HEAD`, and `npm ls fast-check --depth=0` passed; `fast-check` is exactly pinned at `3.23.2` in the manifest, lockfile, and installed tree. Tests preload synthetic settings with `NODE_ENV=test`, bypassing `dotenv.config()` before application imports, so no test depends on the local `.env`.

## Readiness remains closed without deployed facts

**Confirmed.** A direct CLI run with no evidence exited 1 and returned all five failed-check names. A second run with a `--phone` target argument was rejected before evidence access, also exited 1, and emitted no phone value; both outputs contained only sanitized environment, deployment, run, and check identifiers.

Opening the gate still requires an independent collector to observe the deployed public callback, GET verification, `messages` subscription, a correlated valid-signature status, and invalid-signature HTTP 401 with unchanged state, then sign those fresh facts with the collector-only private key.
